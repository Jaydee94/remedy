# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Remedy is an AI operator for a homelab GitOps setup: it reacts to alerts, logs and failed pipelines, analyses root causes and opens pull requests. A human always merges. Authoritative documents: `docs/design.md` (decisions, roadmap, accepted risks) and `docs/research/subscription-cli-usage.md` (terms-of-use constraints). On conflict the design document wins; change the document before changing a decision.

The server needs `REMEDY_DATABASE_URL` (a libpq-style URL or `key=value` string for a PostgreSQL 16 database; `sslmode` and `sslrootcert` travel in it; it holds a password, so it is a `secret.Value`: never in a log, an error, an answer, `values.yaml` or a database column, and the start-up log names only `host:port/dbname`), `REMEDY_ADMIN_PASSWORD` (12+ chars), `REMEDY_RUNNER_TOKEN` (24+ chars) and `REMEDY_MASTER_KEY` (`openssl rand -base64 32`). `REMEDY_DATABASE_MAX_CONNS` (server, default 10, 2 to 100) sizes the connection pool. `REMEDY_DB`, the SQLite file of earlier versions, is gone: a server that finds it set exits with an error that says so. The runner needs the same runner token. Optional: `REMEDY_POLL_INTERVAL` (server, default 60s, at least 10s), `REMEDY_RUN_TIMEOUT` (runner, default 10m) and the limits of automatic diagnosis `REMEDY_DIAGNOSE_COOLDOWN` (15m), `REMEDY_DIAGNOSE_MAX_PER_INCIDENT` (3) and `REMEDY_DIAGNOSE_MAX_PER_DAY` (20, `0` turns it off). `REMEDY_LOG_LEVEL` (server, default `info`; `debug` logs every GitHub request and one line per tool call: run, tool, tool use ID, call ID, kind, replay, refused, never the arguments). The cluster (server only, all optional): `REMEDY_K8S_READ_TOKEN_FILE` turns the read side on, `REMEDY_K8S_WRITE_TOKEN_FILE` with `REMEDY_K8S_WRITE_NAMESPACES` the actions, and `REMEDY_K8S_API`, `REMEDY_K8S_CA_FILE` and `REMEDY_K8S_ARGO_NAMESPACE` say where and how to reach it. A write token file that is missing or empty at start-up is a warning, not an error (a refresher fills it in a cluster): every action fails until it holds a token; a file that holds two lines is still refused. `REMEDY_POLL_INTERVAL`, `REMEDY_DIAGNOSE_*`, `REMEDY_K8S_WRITE_NAMESPACES`, `REMEDY_ALERTMANAGER_URL` (server, empty: the Alertmanager source is off), `REMEDY_ALERTMANAGER_POLL_INTERVAL` (server, default 1m, at least 10s; unset, it takes the value of `REMEDY_POLL_INTERVAL`), `REMEDY_METRICS_URL` (server, empty: the metrics tools and probe are off), `REMEDY_AUTO_APPROVAL_TIMEOUT` (server, default 15m, `0` waits without a limit: how long an approval of an automatic run waits before it expires) and `REMEDY_RUN_TIMEOUT` are defaults: the Setup page overrides them (the control plane reads `REMEDY_RUN_TIMEOUT` too, the chart passes `runner.runTimeout` to both). The Alertmanager token and the metrics token are sealed settings, never environment variables; `REMEDY_ALERTMANAGER_CA_FILE` and `REMEDY_METRICS_CA_FILE` (server, a PEM bundle for an https Alertmanager or metrics store) are bootstrap: read at start-up, a missing file is an error. An allowlist that is empty refuses every cluster action; a write token alone builds the actions. See the README quick start. `REMEDY_ADDR` (default `:8080`) and `REMEDY_DATABASE_URL` move a throwaway server for a browser check: `make web-build`, then `go build -tags webui ./cmd/remedy-server`, point it at a database of its own (a scratch database on the test server of `make pg-up`: `docker exec remedy-pg-testbed psql -U remedy -d postgres -c 'CREATE DATABASE scratch'`, then the URL of `dev/pg/env.sh` with that name; the server makes its tables itself), seed it with `psql` (`docker exec -i remedy-pg-testbed psql -U remedy -d scratch`), and sign in with `getByLabel(/password/i)`. `REMEDY_INTERNAL_ADDR` (server, default empty: one port) moves `/runner/v1` and `/mcp` to a second port, and the main port then answers 404 for them; the runner's `REMEDY_SERVER_URL` must point at the internal one. `REMEDY_RUNNER_STATUS_ADDR` (runner, default empty: no listener) serves `/livez` and `/readyz` for the pod's probes. `REMEDY_AUTH_MODE` (runner, default `subscription`) is read only by the login relay of the Setup page so far, which has no switch of its own: in subscription mode the runner always runs the relay; in any other mode it starts no relay driver (no code that writes to a CLI's stdin) and logs a warning.

A fresh git worktree has no `web/node_modules`: run `make web-install` first, otherwise `make check` fails with `oxlint: command not found`, which looks like a code error. A long-lived checkout (the main one) can also have a stale `web/node_modules` after dependency changes: `make build` then fails with `Cannot find module 'cn'` and similar; run `make web-install` again. Editor diagnostics such as `Cannot find module` or `JSX element implicitly has type 'any'` in a fresh worktree are stale snapshots; `make check` is the authority.

Seeding the database by hand with `psql`: timestamps are text and need nine fractional digits (`2026-10-04T12:00:00.000000000Z`, in SQL `to_char(now() AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS') || '.000000000Z'`), otherwise the API answers 500. Booleans are the integers 0 and 1. An id you give yourself does not advance the table's sequence (the columns are `GENERATED BY DEFAULT AS IDENTITY`): leave `id` out and let it count from 1, or the server's next insert fails on the id you took. Today's feed is ordered by activity id, so insert seed rows oldest first. Live behaviour of a page (the thread's announcements, Today's feed) can be checked by changing rows with `psql` while the page is open: the thread refreshes every 2 to 5 s, Today follows `activity` (columns `at, kind, repo_id, incident_id, run_id, summary, data`).

An incident row also needs `source`, `key` and `title` (since SQLite-era migration 008; the columns are in `001_baseline.sql`). A GitHub row's key is `repo_id || chr(31) || ref || chr(31) || check_name` in SQL; an `alertmanager` or `argocd` row takes its own key and has no `repo_id`. The table refuses a row that has a repository and is not GitHub's, or the reverse. A diagnosed row also needs `diagnosed_at` (since SQLite-era migration 009) for Today's digest and its "Read the diagnosis" link.

Admin sessions are in memory: restarting the server signs everyone out. The next request that answers 401 (the shell polls every two seconds) shows the login page with "Your session ended. Please sign in again."; until then Today's live feed shows "Live updates stopped." with a Reload button.

The Playwright MCP tools save relative screenshot paths and `.playwright-mcp/` in the checkout that launched the browser, not in the current worktree: look for stray `*.png` files there and delete them. Checking `ConfirmButton` (arms on the first click, disarms on blur) needs real Playwright clicks, not `element.click()` in `evaluate`; its ref changes when it re-renders, so confirm with the focused button via `browser_press_key Enter` instead of a second click on the old ref.

`browser_click` and `browser_select_option` take the ref of the latest snapshot as `target` (for example `f12e42`), not a role string: that fails with `Unexpected token while parsing css selector`.

Never `pkill -f 'mcp-config'` (or any loose pattern) to stop a Remedy run's CLI: other `claude` processes on the machine (spike runs) match it. Use the run's own config directory: `pkill -f -- '--mcp-config .*-mcp-[0-9]+/mcp.json'`.

A run's stdout and stderr lines are read concurrently, so their order relative to each other is not guaranteed. Tests may only assert the order within stdout.

The maintainer's shell aliases `ls` to a tool that rejects plain paths; use `command ls` in commands.

The Go tests of the cluster tools run on recordings of a real cluster (`internal/kube/kubetest`, recorded by `dev/kind/record.sh`). After recording again, the ages and counts in the tests need a look (`dev/kind/README.md`). The API server answers `406` to `Accept: text/plain` for a pod log: the client sends `application/json`, which works. Argo CD keeps `operation` at the top level of an Application, next to `spec` and `status` (not in `spec`), and removes it when the operation has ended; its core installation has no `default` AppProject, which the testbed adds.

## Architecture

Two Go processes (module `github.com/Jaydee94/remedy`, `go 1.27.1`) plus a UI in `web/`, and one small third binary: `cmd/remedy-tokenrefresh` (stdlib only; it runs as a CronJob and as a Helm hook in the cluster and mints the write identity's short-lived token). The runner can also serve `/livez` and `/readyz` on `REMEDY_RUNNER_STATUS_ADDR` for the pod's probes. The running version is `internal/version` (`Version`, `Commit`, set with `-ldflags -X`: `make build`, `make images` and the images' `VERSION` and `COMMIT` build arguments in `release.yml` do it; a plain `go build` says `dev`): the sidebar shows it (`GET /api/version`), and the runner reports its own in `POST /runner/v1/status`, so Setup warns when the two differ.

The two processes and the UI:

- **Control plane** (`cmd/remedy-server`): admin API for the UI, runner API, SSE stream, PostgreSQL, a GitHub poller that feeds the incident engine (`internal/poller`, `internal/incident`), a reaper for runs that stay `running` (`internal/reaper`: 15 minutes for a run without gatekeeper access, 2 minutes without a heartbeat for one with it), a responder that diagnoses incidents (`internal/responder`), and the MCP gatekeeper (`internal/gatekeeper`, served at `/mcp`). `internal/app` wires all of it for `cmd/remedy-server` and for the tests that run the whole chain.
- **Runner** (`cmd/remedy-runner`): the only place that holds agent-CLI logins. It dials out to the control plane, long-polls `POST /runner/v1/claim`, runs one CLI subprocess per run in a temp workspace, and posts each output line back as an event (`/runner/v1/runs/{id}/events`, then `/finish`). It has no GitHub, cluster or DB credentials. At start it removes what a killed runner left in its workspace root (`SweepWorkspaces`: only real directories named `<32 hex>-…`, so the root may be shared with other files, but not with a second runner). A run with gatekeeper access also gets a heartbeat (`POST /runner/v1/runs/{id}/heartbeat`, every 10 s): its answer stops the run's time budget while the run waits for an approval (`runClock`) and carries a cancel; a cancel or a 404 stops the agent (the context is cancelled, which `SIGKILL`s the CLI), and a heartbeat that fails never does. In subscription mode (`REMEDY_AUTH_MODE`, the default; there is no switch) it also runs the login relay (`runner.LoginRelay`, a fourth goroutine next to the reporter and the login check): it long-polls `POST /runner/v1/login/poll` for a command (start, code, cancel) and answers with `POST /runner/v1/login/report`, and it drives the unmodified `claude auth login` over pipes. The relay never uses `runner.Execute` and never posts what the CLI prints (that would write the URL into `run_events`); the rules of the sign-in address, the code, the reasons and the session `Manager` are in `internal/loginrelay`, and its `Material` type answers `***` to every `fmt` verb, JSON and `slog`. The control plane serves `GET/POST /api/runner/login` and `POST /api/runner/login/code` and `/cancel` (every answer `Cache-Control: no-store`), holds the claim of runs while a session is open, and writes the activity entries `login_started`, `login_succeeded`, `login_failed` and `login_cancelled` (no URL, no code, no run id).
- **UI** (`web/`): React 19, Vite, TypeScript, Tailwind, React Router and shadcn/ui (components live in `src/components/ui`, imports use the `@/` alias, no `baseUrl`). Reads run events over SSE (`/api/runs/{id}/events`, resumable via `Last-Event-ID`). The Go server embeds `web/dist` only behind the `webui` build tag, so plain `go build`/`go vet` work without a built UI.

Trust boundaries that span several files and are easy to break:

- **Agents get no raw shell and no credentials.** All their actions go through MCP tools of the control plane's gatekeeper (phase 2). Read tools are free; mutating tools block until a human approves in the UI. The agent edits only its local workspace; the control plane pushes branches and opens PRs.
- **Subprocess environment is allowlisted** (`provider.FilterEnv`). `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` must never reach the CLI, otherwise it silently bills the API instead of the subscription. `USER` must stay on the allowlist: on macOS the CLI finds its login in the keychain by user name and otherwise reports "Not logged in". The prompt goes to the CLI via stdin, never argv.
- **Claude CLI invocation** is `claude -p --output-format stream-json --verbose --permission-mode dontAsk --safe-mode --restricted --strict-mcp-config --tools <allowlist> --model <pinned>`. The isolation flags keep the maintainer's global MCP servers (Home Assistant), hooks and plugins away from the agent; `--restricted` ignores the user's settings, so the model must always be pinned. Never add `--bare`: it ignores the subscription login. `--safe-mode` also disables MCP entirely, even servers passed with `--mcp-config --strict-mcp-config` (measured 2026-10-04, CLI 2.1.288): a run that must reach the gatekeeper has to drop `--safe-mode`; `--restricted` alone still keeps user plugins and settings out (only the builtin plugins and the explicit MCP server load). The runner does exactly that for a claim that carries `mcp_token` (`provider.Spec.MCPConfig`): `--mcp-config <file> --allowedTools mcp__remedy`, with the config in a 0600 file in a directory of its own next to the workspace, removed when the run ends.
- **The GitHub token is write-only.** It is sealed with AES-256-GCM (`internal/secret`, key from `REMEDY_MASTER_KEY`, the row ID bound in as additional data), shown only as `…` plus its last four characters, and has a `***` text form (`secret.Value`) so it cannot reach logs or errors. The `github` client is read-only: every exported method is a `Get*` or `List*`, enforced by a test, and `github.New` wraps the HTTP transport so that any method except `GET` and `HEAD` is refused before it is sent. Do not add a write method without a decision recorded in the spec.
- **Admin API:** session cookie (`HttpOnly`, `SameSite=Strict`) plus a required `X-Remedy-CSRF: 1` header on every non-GET. **Runner API:** shared bearer token, constant-time compare. A third domain, `/mcp`, authenticates by a per-run token (see the gatekeeper below). The three are separate middleware and must stay separate.
- **Persistence:** PostgreSQL 16 or newer is the only database (`docs/specs/2026-10-22-postgres-only-design.md`), reached through `pgx/v5`'s `database/sql` adapter by `store.Open` with a pool of `REMEDY_DATABASE_MAX_CONNS` connections (default 10; Open waits up to 30 s for a database that is still starting, and no error of it holds the URL). The store keeps its SQL with `?` placeholders; `internal/store/db.go` wraps the pool and every transaction and rewrites each statement to `$1, $2, ...` once, in a cache capped at 1024 texts (a statement text must therefore be constant: values travel as arguments, never in the text; a literal question mark inside quotes is refused, and the JSONB operators `?`, `?|` and `?&` and `E'...'` strings are not usable). Column types are unchanged: `TEXT` fixed-width timestamps, `INTEGER` 0/1 booleans, `TEXT` JSON; ids are `BIGINT GENERATED BY DEFAULT AS IDENTITY`, repository and host names are unique on `lower(column)`. The schema is `internal/store/migrations/001_baseline.sql` (the state after the last SQLite migration, 018) and the migrations after it (`002_...`), each applied in a transaction of its own that records it in `schema_migrations`; the runner holds a session advisory lock per schema, so two starting processes cannot migrate at once. PostgreSQL's DDL is transactional, so there is no foreign-keys-off mechanism any more. The store's guarantees under a pool of connections (the claim of a run, the limits of automatic diagnosis, the approval compare-and-set, the ordered activity feed) are listed with their mechanisms in `docs/research/postgres-concurrency-audit.md`. `internal/store` is the only package that issues SQL. The graph (phase 3) lives in the same DB behind an interface. A run's events are always posted before `finish`, and the SSE handler reads run status before events; that ordering is what guarantees a client sees every event before `done`. Today's feed reads the append-only `activity` table, and its SSE stream follows that table by id (it polls, there is no hub): write activity in the same transaction as the state change it describes, and never reuse or backfill ids.
- **Incidents** have a source (`github`, `alertmanager`, `argocd`) and are keyed by `(source, key)` while they are not resolved; for GitHub the key is `store.GitHubKey(repo, ref, check name)`, which the migration also computes in SQL (a test pins both to the same string). Only a GitHub incident has a repository. `incident.Observation` carries any source, and the engine opens, touches and resolves by key. Every state change writes its `activity` entry in the same transaction. The poller must stay idempotent (a second cycle on the same GitHub state changes nothing) and must not resolve PR incidents from a full page of 100 PRs, which may be truncated. Inside `Store.inTx` use only the `tx`: the store has a pool of connections, so a call on `s.db` there runs on another connection, outside the transaction, and breaks its atomicity (with the old single SQLite connection such a call deadlocked and showed at once; with a pool it passes silently, so review for it). `inTxIso` runs a transaction at another isolation level and runs it again after a serialization failure (SQLSTATE `40001`), so its function must be idempotent. `GET /api/runs?incident=` leaves `prompt`, `result` and `output` out of responder runs (cleaned GitHub data, the whole diagnosis); `GET /api/runs/{id}` has them.
- **Everything from GitHub that reaches an agent is untrusted data.** `internal/prompt` is the only place that builds the prompt: it cleans, redacts (`internal/redact`) and bounds the data and puts it in blocks with a random delimiter, while the instructions stay outside. The control plane validates the agent's answer (`diagnosis.Parse`, strict; `responder.CheckOutcome` in `finish`) and the UI shows it as text: its prose (diagnosis fields, an answer) through the restricted Markdown renderer `web/src/agenttext.ts` + `components/AgentText.tsx` only (React elements, no HTML, no link or image, no page heading; `docs/specs/2026-10-22-agent-text-markdown-design.md`), never through a Markdown library or `dangerouslySetInnerHTML`; arguments, commands, notes and run output stay exact text. The repository snapshot goes through the control plane, which filters secret files (`snapshot.Filter`); the runner unpacks it with `snapshot.Unpack`, which refuses path traversal and extracts only symlinks with a relative target without `..`. The runner never holds a GitHub token. A change to any of this needs the care the token handling gets. Automatic diagnosis must stay within its limits: they are checked inside one store transaction (`StartDiagnosis`), not around it. A question about an incident (an ad-hoc run with `incident_id`) is framed at the claim by `prompt.Question`; `runs.prompt` stays the bare question, and no incident text is in the prompt: the agent reads it through `incident_get` as data.
- **The gatekeeper** (`internal/gatekeeper`, `POST /mcp`) is the only way an agent acts. A run's token is minted when the run is claimed (`Store.MintRunToken`), kept only as a hash, and revoked in the transaction that ends the run (`closeRunTx`, which also abandons the run's waiting calls). Every call is a `tool_calls` row, identified by `(run, claudecode/toolUseId)`: a repeat of it (the CLI replays an in-flight call after `SIGTERM`) must never become a second approval or a second execution. A mutating tool answers with an event stream and MCP progress notifications until the decision; `Store.BeginExecution` is the compare-and-set that lets exactly one handler run the stored arguments, and `Gatekeeper.Decide` refuses when no handler waits (an approved action would have no one to receive its result). A mutating call of an automatic run expires after `auto_approval_timeout` (`tool_calls.expires_at`, the gatekeeper's timer): `Store.ExpireCall` is a compare-and-set against `Decide` (only a call that still waits with its decision pending moves, an approved call never expires), so exactly one of the decision and the expiry wins, and the agent is told that nothing was run. A new tool needs a strict `Decode`, a `Check` for preconditions that would waste an approval, and its result goes through `sanitize` (redaction, 32 KB). Agent-written text (arguments, notes) is untrusted.
- **Cluster credentials** (`internal/kube`) belong to the control plane alone: two token files (a read identity and a write identity), read again at every request because service account tokens rotate, and never in a log, an error, an API answer or a database column. The `Reader` is GET-only and the `Writer` has exactly four methods (restart a workload, delete a pod, refresh and sync an Argo CD application) and refuses a namespace outside the allowlist; the transports and tests enforce both. A new method needs a decision recorded in `docs/specs/2026-10-04-phase-2c-cluster-design.md`. Tools of the group `cluster` are offered only to runs started with `runs.cluster`, and a run that is not offered a tool gets the answer for a tool that does not exist. The cluster read tools (`internal/gatekeeper/tools_cluster.go`) open every result with a note that it is data, show environment variable names but never values, show no annotations, and cannot reach Secrets: there is no tool for them and the read identity has no right to them. The action tools (`tools_cluster_actions.go`) check the namespace allowlist before an approval is asked for and again when they run; for Argo CD the allowlist is checked against the application's destination namespace, because RBAC cannot say it; `cluster_delete_pod` refuses a pod that was made after the approval was asked for (`Call.RequestedAt`, second resolution, so a pod of the same second is refused too); a sync never prunes, forces or replaces.
- **The Alertmanager client** (`internal/alertmanager`) is read-only like the GitHub and kube readers: `GET` and `HEAD` only, no redirects, no proxy, and the bearer token is opened per request from the sealed secret setting (`alertmanager_token`: sealed with the master key, write-only, never shown beyond its hint). The metrics client (`internal/metrics`, a Prometheus-compatible query API, bearer token only, `metrics_token`) holds to the same rules. A source's incidents are resolved only after a complete, successful fetch (and a successful read of the hosts): a failed, cut-off or oversized answer resolves nothing.
- **Host credentials** (`internal/sshhost`, tables `hosts` and `host_credentials`) belong to the control plane alone: a private key, its passphrase or a password is sealed like the GitHub token (`store.HostCredentialAAD`, bound to the host id; its value never changes), shown only as a hint, and never in a log, an error, an API answer or an activity entry. `sshhost.Dial` talks only to a host that presents exactly the pinned key; `Probe` stops at the key exchange and sends no login; pinning is a separate call that names the fingerprint the maintainer compared. Cycle 1 ran only the four constant test commands; `sshhost.Service.Exec` (cycle 2) runs the host tools' commands. The onboarding snippet validates every value it writes into a `sudoers` file (`sshhost.Snippet`). `sshtest` is an SSH server for tests; `REMEDY_BROWSER_SSH=1 go test ./internal/sshhost -run TestServeForBrowser -v -timeout 0` serves one for a look at the UI (it answers the canary and `docker ps -a`).
- **Host tools** (`internal/hostexec`, `internal/gatekeeper/tools_host.go`, `internal/app/hostaccess.go`) are the one barrier on a host that Remedy owns. `host_read` runs only a form of the table in `hostexec/classify.go` exactly (no general file reader; nothing outside the table can be added by a skill, an agent or a host field); `host_change` takes any argv that is not on the never-list (`hostexec/never.go`, checked before the approval, again in `Run`) and runs `sudo -n -- ...` after an approval that shows the command word for word. The argv travels as single-quoted words; a canary (`hostexec.CanaryCommand`) proves in every connection that the account's shell reads them like a POSIX shell, or nothing else is sent (`Exec` without a canary is `ErrShell`, fail closed). A host that changed after the question (`hosts.updated_at` after `Call.RequestedAt`, second resolution) makes an approved call refuse. The gatekeeper package holds no credential: `app.HostAccess` opens the login. Output is data (`hostexec.DataLine`), `docker inspect` loses the values of `Config.Env` and `ContainerConfig.Env` (a templated `--format` inspect shows a fixed text), and a connection failure reaches the agent as a fixed sentence. The never-list is hardened (paths cleaned, long-option prefixes, shell tokens split; `su`, `doas`, `nsenter`, `chroot` refused), `ChangeCheck` takes one container or unit at a time for `docker`/`systemctl` `start|stop|restart`, and a name of only hex digits is never a container (docker resolves ID prefixes). A `host_change` that timed out (`gatekeeper.executeTimeout`, 75 s; the command gets SIGTERM) or was lost after it started (`sshhost.ErrTimeout`, `ErrLostAfterStart`: the command was sent) has an UNKNOWN outcome and the answer says so, with no retry wording; a dial or canary failure is `ErrUnreachable` (nothing was sent).
- **Skills** (`internal/skill`, table `skills`, tool `skill_get`, block `available_skills`) inform an agent's reasoning and nothing else: no skill widens the table of `host_read`, removes an approval or changes a limit (those are Go code; `internal/app/skills_chain_test.go` proves it). A run with gatekeeper access sees only the `active` skills that are global or belong to its hosts (`store.VisibleSkills` for the responder when it starts, `store.RunSkills` at the claim of an ad-hoc run and in `skill_get`); a proposal (`state = 'proposed'`, made only by `store.CreateProposals`, which redacts, validates the raw text first, cuts a text the redaction made longer and bounds the evidence), an `off` skill and another host's skill are never listed or loadable, and a proposal is invisible until the maintainer confirms it (`store.ConfirmSkill`; a replacing proposal overwrites the replaced skill's text). The prompt lists names and descriptions only, in a data block with the random delimiter (`prompt.SkillsSection`); a body is loaded by `skill_get` (`host` is a host's name or `(global)`) as framed, redacted data (`sanitize`). `internal/skill` refuses control and invisible characters (every Unicode format, separator and private-use character, variation selectors, U+034F) and the prompt text is hardened again. A written skill is the maintainer's text; a proposal is untrusted until he confirms it. Deleting a host deletes its skills (`ON DELETE CASCADE`). **The learning run** (`internal/learner`, role `learner`) is the only producer of proposals: the agent is offered `host_list`, `host_read` and `skill_get` and nothing else (`learnerTools` in `internal/gatekeeper/tools.go`, an allowlist by name checked in `offeredTo` before the group; any other call answers like an unknown tool, and the refusal of `host_read` does not point a learner at `host_change`) and has no way to store anything. A skill the maintainer turned off is not listed in its prompt either, and a proposal under the name of an off skill replaces that skill. `learner.CheckRun` judges its answer at `finish` with the strict `diagnosis.ParseLearn` (a token walk: exact keys, no duplicates, no nulls, fixed error texts; an invalid answer fails the run with `invalid_output`); `learner.Complete` then stores the profile (one note `profile` whose headings Remedy writes, `learner.ProfileBody`: agent text flattened, a leading Markdown block marker escaped, always cut to fit 8 KiB: notes first, then containers, then services) and the skills through `store.CreateProposals`, after checking every cited command against the run's own succeeded `host_read` calls (exact argv, `ran` true or false; a command that did not run is shown as "not run"). `Complete` is idempotent (`store.LearnOutcomeRecorded` and a mutex; the `Learner` is used by pointer). A failed, cancelled, timed-out or lost run stores nothing and logs `learn_failed` with a fixed sentence, never agent text. A run starts only for a host that is enabled, has a login, a pinned key and status `ok`, when no run is queued or running and at most 11 proposals wait for the host; at most 20 proposals wait per host (`skill.MaxPendingPerHost`, backstop `store.ErrTooManyProposals`). The prompt, result and answer of a learner run are left out of `GET /api/runs`, which names its host. `internal/app/learner_chain_test.go` proves that an instruction printed by a host becomes a proposal only and that a confirmed one still cannot widen `host_read` or remove an approval.

## Hard rules

- Never read, copy, log or store the agent CLIs' credentials; only start the unmodified binary (terms of use). One narrow, named exception (`docs/design.md` 2.7.1, approved on 2026-10-21 with `docs/specs/2026-10-21-ui-login-relay-design.md`): the login relay of the Setup page passes the authorization URL of `claude auth login` and the one-time code through the control plane and the runner, in memory only, for one attempt, never in a database row, an activity entry, a log line, an event, an error or an answer to a browser (the code is write-only); nothing the CLI writes in its config directory is ever read, and tokens never pass through Remedy.
- No auto-merge, no force-push (additional commits only; abort on new foreign commits).
- Logs, alert text, PR text and commit messages are untrusted input and never go to an agent as instructions.
- Secrets are redacted before anything is handed to a CLI. Repository files are handed over as they are, minus `.env*`, `*.pem`, `*.key` and `id_rsa*`; a secret committed elsewhere reaches the agent (accepted in the spec).
- No multi-user operation and no third-party access through the subscription logins.

## Conventions

- Everything in the repo is English: docs, plans, code, comments, commit messages, UI copy. Conversation with the maintainer may be in German.
- Pull request titles are conventional commits (`feat:`, `fix:`, `docs:` ...): the squash title decides the release. A `[skip ci]` in a commit message skips the release run of that merge.
- Go: stdlib-first (`net/http` method patterns, `log/slog`). A new dependency needs a reason; today there are `github.com/jackc/pgx/v5` (the PostgreSQL driver, pure Go) and `golang.org/x/crypto`.
- `web/tsconfig.app.json` sets `erasableSyntaxOnly` and `verbatimModuleSyntax`: no enums or constructor parameter properties, and `import type` for types.
- UI: a button that starts a request keeps the keyboard focus (`aria-disabled` plus a guard in the handler, not `disabled`); when a control unmounts after an action, `useFocusRestore` returns the focus to the page heading; the thread's live region announces by key (`useAnnouncement`) so an old message is never repeated.
- Test first for logic with behaviour (incident correlation, redaction, gatekeeper). Runner tests use a fake `claude` shell script from `internal/testutil` instead of the real CLI.
- A migration that changes existing data gets a test on a database built from the earlier schema, with a row in every table that points at the changed one. The old model (`migrate008_test.go`, which built a SQLite database from the migration files) is gone with SQLite; `internal/store/schema_test.go` is the model now: it works on a fresh schema of the test server, fills one row into every table (`seedGraph`) and checks the result; `Store.migrateFS` takes the migration files as an `fs.FS` (those tests feed it a `fstest.MapFS`), so a test of a data migration applies the earlier files, fills its rows and then applies the new one.
- All Go tests need a PostgreSQL 16: `REMEDY_TEST_DATABASE_URL` names it (`dev/pg/README.md`). `make test` (and so `make check`) starts a throwaway container with `dev/pg/up.sh` when the variable is unset and docker exists; `make pg-up` and `make pg-down` do it by hand. Each test gets a schema of its own (`internal/testutil/pgtest`, `testutil.Store`) that is dropped afterwards, so packages run in parallel against one server. A test that needs the database and cannot reach it fails; it never skips silently (the helm render tests are the one deliberate skip). CI runs a `postgres` service.
- Fake `claude` scripts and other shell in tests run on macOS locally but on Linux in CI: no BSD-only flags (`stat -f`, `sed -i ''`, `date -j`); try the GNU form first (`stat -c %a ... || stat -f %Lp ...`).
- In a worktree-isolated Claude Code session the Bash tool refuses commands with variables in the program position, `cd` into another checkout, or text that mentions git (also `gh` with a `--jq` expression or command substitution). Write such logic into a script file with the Write tool (not a heredoc in the same command) with literal paths (scratchpad) and run `sh /literal/path/script.sh` as its own command. Check that a new file name is free before creating it (`internal/server/activity.go` already existed).
- `EnterWorktree` branches from the local `origin/main`: run `git pull` in the main checkout after each merged PR and before entering the next worktree, otherwise the new PR conflicts with the one just merged.
- A worktree made with `EnterWorktree` stays locked by its session: `ExitWorktree remove` and `git worktree remove` fail after the merge, and `gh pr merge --delete-branch` skips the local branch. Remove both by hand after the session ends; to go on in the same worktree, `git fetch`, then `git checkout -b <name> origin/main` (uncommitted files come along).
